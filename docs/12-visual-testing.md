# Визуальное тестирование

## Зачем

Скриншот-тесты ловят регресс вёрстки, который не видят ни API-, ни обычные E2E-тесты: сдвинулся блок, поехали отступы, пропал цвет кнопки. Именно так был бы пойман BUG-009 (затемнённая страница) даже без проверки кликов.

## Запуск

```bash
npm run test:visual          # сравнить с эталонами
npm run test:visual:update   # перегенерировать эталоны (когда изменения согласованы)
```

## Что покрыто

| Тест | Что снимает |
|---|---|
| VIS-01 | главная страница целиком |
| VIS-02 | модальное окно товара |
| VIS-03 | корзина с двумя позициями |
| VIS-04 | форма оформления заказа |
| VIS-05 | страница входа в админку |

## Как обеспечена стабильность

1. **Отключены анимации** — `toHaveScreenshot.animations: 'disabled'`.
2. **Спрятаны тосты** — динамические уведомления скрываются через `addStyleTag` перед снимком.
3. **Только статичные экраны** — не снимаем админку с заказами, где меняются числа и даты.
4. **Фиксированный вьюпорт** — 1280×800, `deviceScaleFactor: 1`.
5. **Допуск** — `maxDiffPixelRatio: 0.01`.

## Важно: эталоны привязаны к платформе

Playwright добавляет суффикс платформы: `storefront-visual-chromium-win32.png`. Это значит:

- Эталоны, сгенерированные на Windows, **не подойдут** для Linux в CI.
- В `ci.yml` job `visual-tests` запускается на `windows-latest` и помечен `continue-on-error: true`.
- Если добавите Linux-раннер — сгенерируйте эталоны заново на нём: `npm run test:visual:update` и закоммитьте `*-linux.png`.

## Рабочий процесс при изменении дизайна

1. Внести правки
2. `npm run test:visual` — посмотреть, что «поехало»
3. Убедиться, что разница ожидаемая
4. `npm run test:visual:update` — обновить эталоны
5. Закоммитить новые `.png` вместе с изменениями кода

⚠️ Никогда не обновляй эталоны «просто чтобы позеленело» — это убивает смысл тестов.
