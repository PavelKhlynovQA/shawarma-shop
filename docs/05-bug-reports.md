# Баг-репорты «Шаурма-Мастер»

Все дефекты ниже **реально воспроизведены** на текущей сборке (13.11.2026, БД SQLite, `npm start`).


## BUG-001. Admin API: нечисловой параметр `limit` приводит к 500

**Приоритет:** Major · **Серьёзность:** S2 · **Связано:** TC-040

**Окружение:** Windows 11, Node 26.13, SQLite, `npm start`

**Предусловия:** есть токен администратора.

**Шаги:**
1. Войти: `POST /api/auth/login` с `admin@shawarma.ru / Admin123!`
2. Выполнить `GET /api/admin/orders?limit=abc` с заголовком `Authorization: Bearer <token>`

**Фактический результат:**
```json
HTTP 500
{"error":{"code":"INTERNAL_ERROR","message":"Внутренняя ошибка сервера","details":null}}
```
В лог падает `RangeError: Invalid limit value` от драйвера SQLite.

**Ожидаемый результат:** `400 VALIDATION_ERROR` с указанием поля `limit`, либо игнорирование параметра и дефолт 50.

**Причина:** `Math.min(Number(req.query.limit), 200)` возвращает `NaN`, который уходит прямо в SQL.

## BUG-002. Admin API: отрицательные `limit` и `offset` принимаются молча

**Приоритет:** Minor · **Серьёзность:** S3 · **Связано:** TC-040

**Шаги:**
1. `GET /api/admin/orders?limit=-5`
2. `GET /api/admin/orders?offset=-100`

**Фактический:** оба запроса возвращают `200` и полный список заказов. В SQLite `LIMIT -5` означает «без ограничения».

**Ожидаемый:** `400 VALIDATION_ERROR` — параметры должны быть неотрицательными целыми.

**Риск:** на PostgreSQL поведение отличается (`LIMIT -5` → ошибка 500), то есть дефект ещё и ломает совместимость двух драйверов.

## BUG-003. Проверка промокода отдаёт `null` при нечисловой сумме

**Приоритет:** Major · **Серьёзность:** S2 · **Связано:** TC-026

**Шаги:**
1. `POST /api/promo/validate` с телом `{"code":"SHAWARMA10","subtotal":"abc"}`

**Фактический:**
```json
HTTP 200
{"promo":{"code":"SHAWARMA10","discountPercent":10,"discount":null,"total":null}}
```
`NaN` сериализуется в JSON как `null`.

**Ожидаемый:** `400 VALIDATION_ERROR`, поле `subtotal` — «должно быть числом».

**Влияние:** клиент получает `null` и падает при форматировании суммы; на UI это выглядит как «Итого: null ₽».

## BUG-005. Заказ читается по номеру без авторизации — раскрытие персональных данных

**Приоритет:** Critical · **Серьёзность:** S2 · **Связано:** TC-038

**Шаги:**
1. Создать заказ: `POST /api/orders` (гость, телефон `+79995554433`, адрес «ул. Секретная, 1»)
2. Из ответа взять `publicId`
3. Выйти из аккаунта / открыть приватное окно
4. `GET /api/orders/{publicId}` без заголовка `Authorization`

**Фактический:**
```json
HTTP 200
{"order":{"publicId":"SH-261113-FED0","customerName":"Секретов Секрет","phone":"+79995554433","address":"Волгоград, ул. Секретная, 1", ...}}
```

**Ожидаемый:** доступ только владельцу заказа или администратору; для гостя — подтверждение по последним 4 цифрам телефона.

**Влияние:** утечка ФИО, телефона и адреса. Номер вида `SH-261113-FED0` имеет низкую энтропию — перебором можно собрать базу клиентов.

## BUG-006. Создание заказа не обёрнуто в транзакцию

**Приоритет:** Major · **Серьёзность:** S2 · **Связано:** US-03

**Шаги:**
1. Смоделировать сбой между `INSERT INTO orders` и `INSERT INTO order_items` (например, прервать процесс в отладчике или искусственно уронить вставку позиции)
2. Открыть админку

**Фактический:** в `orders` остаётся заказ с корректной суммой, но без позиций в `order_items`; история статусов также может отсутствовать.

**Ожидаемый:** заказ создаётся целиком или не создаётся вовсе (atomic).

**Причина:** каждый `db.run` выполняется отдельно, `BEGIN/COMMIT` не используются.

## BUG-007. Лимит использований промокода не защищён от гонки

**Приоритет:** Minor · **Серьёзность:** S3 · **Связано:** BR-06

**Шаги:**
1. Создать промокод с `usage_limit = 1`
2. Отправить два запроса `POST /api/orders` с этим промокодом одновременно (`Promise.all`)

**Фактический:** оба заказа создаются со скидкой, `used_count` становится `2` при лимите `1`.

**Ожидаемый:** второй заказ отклоняется с `PROMO_LIMIT_EXCEEDED`.

**Причина:** проверка лимита и инкремент счётчика не атомарны.

## BUG-009. Атрибут `hidden` не скрывает модальные окна — оверлей перехватывает все клики

**Приоритет:** Blocker · **Серьёзность:** S1 · **Найден:** E2E-тестом (cart.spec.js)

**Окружение:** Chromium 131, страница `/`

**Предусловия:** приложение запущено, витрина загружена.

**Шаги:**
1. Открыть http://localhost:3000/
2. Попробовать нажать «В корзину» на любой карточке

**Фактический результат:**
- Вся страница затемнена полупрозрачной подложкой, в центре экрана висит пустая панель.
- Клики по кнопкам и вкладкам не срабатывают — их перехватывает `.modal__backdrop`.
- В DOM: `<div hidden class="modal" id="checkoutModal">`, при этом `getComputedStyle(...).display === "grid"`.

**Ожидаемый результат:** скрытые модалки не отображаются и не участвуют в перехвате событий.

**Причина:** в `styles.css` задано `.modal { display: grid; }`. Авторский стиль перебивает агентский `[hidden] { display: none }`, поэтому атрибут `hidden` игнорируется.

**Исправление:**
```css
[hidden] { display: none !important; }
```

**Доказательства:** `docs/screenshots/bug-009-before.png` (до) и `bug-009-after.png` (после).

**Связано с:** TC-001, TC-008, E2E-10

**Важность:** дефект полностью блокирует работу с витриной в браузере, но **не виден API-тестам** — 24 автотеста и ручные запросы были зелёными. Найден только E2E.

## BUG-010. Неверный пароль в админке не показывает ошибку

**Приоритет:** Major · **Серьёзность:** S2 · **Найден:** E2E-тестом (admin.spec.js, E2E-31)

**Шаги:**
1. Открыть `/admin`
2. Ввести `admin@shawarma.ru` и пароль `wrong-password`
3. Нажать «Войти»

**Фактический результат:**
- Сообщение «Неверный email или пароль» не появляется.
- Форма логина просто перерисовывается.
- В консоли браузера — необработанный `Uncaught (in promise) Error: Сессия истекла, войдите заново`.

**Ожидаемый результат:** красный тост с текстом `Неверный email или пароль`, форма остаётся заполненной.

**Причина:** в `public/admin.js` функция `api()` на любой `401` стирает токен, вызывает `renderLogin()` и выбрасывает исключение. Для запроса `/api/auth/login` это неверно: `401` там означает «неверные учётные данные», а не «истёкшая сессия», поэтому ветка показа ошибки недостижима.

**Исправление:**
```js
if (response.status === 401 && token) { ... }
```
Автовыход срабатывает только когда токен действительно отправлялся.

**Связано с:** TC-035, E2E-31
