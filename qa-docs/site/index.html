Тест-план

Цели тестирования

Убедиться, что функциональность интернет-магазина соответствует требованиям, а критические бизнес-сценарии (заказ, оплата, уведомление) работают без потери данных.

  • Проверить корректность расчётов: суммы заказа, скидки, минимальная сумма доставки
  • Проверить статусную модель заказа и невозможность недопустимых переходов
  • Проверить разграничение доступа между гостем, покупателем и администратором
  • Проверить целостность данных в БД после бизнес-операций

Объект и границы тестирования

Объект: REST API, витрина (SPA), админ-панель, база данных PostgreSQL.

  • В scope: функциональность меню, корзины, заказов, оплаты, промокодов, авторизации по телефону, админки
  • В scope: API-контракт, коды ответов, формат ошибок, заголовок X-Request-Id
  • В scope: целостность данных и корректность агрегатов в БД
  • Не в scope: реальный эквайринг, SMS-шлюз, нагрузочное тестирование выше 100 RPS, мобильные приложения

Стратегия по уровням

Используется четырёхуровневая пирамида: от быстрых проверок контракта до сквозных сценариев в браузере.

  • Smoke (4 теста): доступность сервиса, меню, дополнительные ингредиенты, обработка неизвестного маршрута
  • API (23 теста): контракт, бизнес-правила, негативные сценарии, права доступа
  • E2E (35 тестов): витрина, корзина, оформление, оплата, админка, сквозной путь покупателя
  • Визуальные (5 тестов): эталонные скриншоты ключевых экранов
  • БД: ручные SQL-проверки целостности после операций

Техники тест-дизайна

  • Эквивалентные классы — суммы заказа, промокоды, роли пользователей
  • Граничные значения — 499/500/501 ₽, количество 0/1/20/21, пароль 5/6 символов
  • Таблица переходов — статусы заказа NEW → CONFIRMED → COOKING → DELIVERING → DONE
  • Попарное тестирование — способ получения × промокод × авторизация
  • Анализ рисков — приоритет деньгам и персональным данным

Критерии входа и выхода

Критерии входа (DoR): сборка запускается локально, база наполнена демо-данными, известны тестовые учётки и промокоды.

  • Критерии выхода (DoD): пройдены 100% smoke-тестов
  • Пройдено не менее 95% кейсов высокого приоритета
  • Нет открытых дефектов уровня Blocker/Critical
  • Автотесты зелёные: API 23/23, E2E 35/35, визуальные 5/5

Риски и митигация

  • Нет транзакций при создании заказа → частично записанный заказ (BUG-006). Митигация: проверка при сбое, приоритетный баг
  • JWT живёт 24 часа без refresh → обрыв сессии. Митигация: негативные тесты токена
  • Публичный доступ к заказу по номеру → утечка ПДн (BUG-005). Митигация: security-проверка перед релизом
  • Зависимость от демо-данных → тесты ломаются при изменении меню. Митигация: данные через API, справочник товаров

Окружения и инструменты

Тестирование проводится на трёх окружениях: локальном (SQLite), Docker (PostgreSQL) и CI (GitHub Actions).

  • API и E2E: Playwright + node:test, база SQLite или PostgreSQL
  • Ручные проверки БД: DBeaver, SQL-запросы из раздела «Тест-кейсы БД»
  • Отчётность: Allure, HTML-отчёт Playwright, артефакты в GitHub Actions
  • Документация: Confluence (экспорт в этой папке), Jira (CSV для импорта)

Отчётность и метрики

  • Покрытие требований тест-кейсами — 100%
  • Плотность дефектов по модулям
  • Время прогона регрессии: API ~2 с, E2E ~40 с, визуальные ~7 с
  • Ежедневный статус: количество пройденных кейсов, найденные дефекты, блокеры
